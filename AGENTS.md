# Repository instructions

## Google Docs editing

- Use the Google Drive/Docs MCP, not browser automation, for reads and edits.
- Treat the latest local Markdown draft as the content source unless the user says otherwise; read the whole relevant document before syncing.
- Read the Doc’s text, tables, tab ID, and revision immediately before editing. Prefer targeted range edits and use revision-controlled batch updates.
- Preserve native tables, lists, equations, and deliberate Google-Doc-only figures. Equation images are acceptable when native math will not render reliably.
- Apply standard Google Docs named styles explicitly. After insertions, check that body paragraphs did not inherit heading styles.
- After editing, reread the Doc and reconcile key phrases and section structure against the Markdown source. Verify the Drive title separately from the visible document title.
- For visual QA, export to PDF when practical; use the Drive download action for exports that exceed the normal 10 MB export limit.

## Research-paper claim discipline

- State definitions directly.
- Scope “the model shows” to results established by an implemented construction.
- For stipulated-update results, say “the construction reproduces” and name the stipulation in the same sentence.
- Introduce formal interpretations with “can be read as” or “offers a candidate account.”
- State untested clinical mechanisms as proposals, not established causes.
- Phrase discriminating, untested claims as predictions.
- Reserve “derive” for implemented derivations that passed their declared tests; use “follows within the account” for conceptual entailments.
- State falsifications and implementation deadlocks where the affected claim appears, not only in the results or limitations.
- Do not let main-text certainty outrun the limitations or simulation-status appendix. If a mechanism failed derivation, describe it as a hypothesis or obstruction.
